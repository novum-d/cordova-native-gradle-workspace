# WebView検証前にWeb側へ確認する事項

[ドキュメント一覧](README.md) · [Vueの取り込み方針](VUE_WEBVIEW_INTEGRATION.md) · [全体仕様](CLIENT_API_SPEC.md) · [セキュリティ条件](WEBVIEW_BRIDGE_REVIEW.md)

更新日: 2026-10-25。Web担当へ共有する質問を、既存Vueの組み込み検証前に確認する内容と、業務APIの実装までに決める内容に分けています。回答を受領した記録ではありません。

[手書きHTMLの単体通信サンプル](WEBVIEW_BRIDGE_SAMPLE.md)は実装しました。以下の質問は、次の既存Vue組み込み・業務API実装に向けたものです。

## 最初に共有する前提

以下はこちらで整理している設計前提です。Web側では、現行実装と衝突する制約があれば共有をお願いします。

- 起動元は既存CordovaのWebView、起動先はfeatureの既存MainActivityに置く標準WebViewです。別アプリからのActivity起動も要件に含みます。
- 起動先ではVueの画面コードを再利用し、ビルドしたHTML・JS・CSS等をAndroid assetsへ同梱します。2つのWebView間でVue・Store・認証状態は自動では共有されません。
- 画面切り替えは単一index.html上のVue Routerで行い、起動先ではハッシュ方式を基本とします。
- 起動先の通信はNativeBridge.postMessageとJavaScriptReplyProxy.postMessageを使い、READY後に接続を確立します。Cordova側のActivity起動処理は維持します。
- 初回の通信検証はGET https://jsonplaceholder.typicode.com/users/1 と、タグIDがABC123の疑似NFCイベントを使います。実際のNFC・Camera処理は対象外です。
- 業務の確定範囲はゴルフ場ID・ホルダー番号の読み取りで、処理IDはgolf-change.read-holderです。NFC書き込みは対象外です。

## A. 既存Vueの組み込み検証前に確認する質問

### A1. Vueソースと再現可能なビルド情報を共有できますか

対象リポジトリ・ディレクトリ、検証に使うブランチまたはコミット、Vue・Vue Router・ビルドツールの版、必要なNode・パッケージマネージャーの版、依存固定ファイル、インストール／ビルドコマンド、成果物の出力先を教えてください。既存の開発・CI手順があれば、その参照先でも構いません。

目的: 既存の版を維持して同じ成果物を作り、必要なJS・CSS・遅延ロード用chunkを一式で取り込むためです。このAndroidリポジトリには、現在Vueソースやそのビルド定義がありません。

### A2. どの画面・コンポーネントを検証用に切り出せますか

再利用する画面のファイル・ルート名と、起動に必要なStore・ルートガード・ログイン・初期API取得などの依存を教えてください。既存Routerの履歴方式、base／publicPath、ハッシュ方式で動かす際の制約も確認したいです。最初に表示できる最小のサービス画面または検証画面を指定してください。

目的: アプリ全体の初期化をどこまで必要とするかと、単一index.htmlでの初期表示・画面切り替えの確認範囲を決めるためです。

### A3. Cordovaへ直接依存している処理はどこにありますか

対象画面や起動処理で使うCordovaPlugin、cordova.exec、deviceready、その他Cordova固有APIの一覧と呼び出し箇所を教えてください。既存のクライアントAPIラッパーがあれば、その定義と使用例も共有してください。標準WebView向けの通信アダプターを追加する際の変更担当も確認したいです。

目的: Vueの画面コードを共有しながら、CordovaのActivity起動と標準WebViewのWebMessage通信を接続するためです。

### A4. 検証画面はログインなしで起動できますか

ログインや事前データが必要な場合は、認証方式、必須の初期データ、検証用モックの可否を教えてください。画面が呼ぶAPIのURL・接続先一覧、相対/apiや開発用proxyへの依存、https://appassets.androidplatform.net からのアクセスに関するCORS・Cookie等の制約も確認したいです。

目的: 起動元と起動先が別のWebViewになる条件で、画面を表示して通信検証できるか判断するためです。認証情報そのものは質問票へ記載せず、必要時に合意した方法で共有してください。

### A5. WebView向け成果物の作成・受け渡しは誰が担当しますか

Android側がVueソースからビルドするか、Web側のCI等で作成した成果物を受け取るか、現行の運用に合う方法を教えてください。既存Cordova向け成果物と標準WebView向け成果物を作り分ける際の担当・受け渡し先・バージョン識別方法も確認したいです。

目的: ファイルの手動コピーに依存せず、検証したWebとAndroidの組み合わせを再現できるようにするためです。

### A6. 最初の共同確認に使う画面と担当を決められますか

API実行・受信結果表示・疑似NFCイベント表示を既存Vueのどの画面へ置くか、または独立した検証画面にするかを教えてください。API失敗、不正メッセージ、reload、画面遷移後のイベント受信を一緒に確認するWeb側の担当・確認可能なタイミングも共有してください。

目的: 今回の完了条件を、Web側の操作とAndroid側の受信・送信の両方で確認するためです。READY・USER_FETCHED・NFC_DETECTEDの検証用データは[レビュー文書](WEBVIEW_BRIDGE_REVIEW.md)を共通のたたき台にします。

## B. 業務APIの実装までにWeb側と決める質問

以下は、単体の双方向通信検証を始めるための必須回答にはしません。

| ID | 質問 | 決める内容 |
| --- | --- | --- |
| B1 | 業務クライアントAPIを、画面からどのような名前・呼び方で利用したいですか | 既存ラッパーとの整合、Promise／callback、要求と最終結果、途中イベントの受け取り。typeと処理IDを区別したJSON例 |
| B2 | ゴルフ場ID・ホルダー番号の読み取りで、Webが渡す引数と受け取りたい結果は何ですか | フィールド名・型・必須項目、表示・送信先、先頭ゼロ等の保持要件。2項目は取得対象であり、起動の必須引数にはしない前提 |
| B3 | 起動要求の受信から読み取り開始・終了まで、画面はどう動きますか | 初期ルート、案内表示、読取開始の契機、結果表示、終了後に戻る先。画面の再描画と実処理の再実行を区別する |
| B4 | 戻る・別画面への遷移・連続実行時に、実行中処理をどう扱いますか | 継続／取消、二重押下・並行要求、タイムアウト、再試行、古い結果の扱い |
| B5 | 起動元との間で共有が必要な状態は何ですか | 認証、利用者・施設情報、処理結果の返却先。必要最小限のデータと受け渡し方法 |
| B6 | 実サービスの通信先・CSP・ログ出力に関する制約はありますか | 許可するAPI・画像等の配信先、外部scriptやv-html等の使用箇所、検証用と本番用のログの差 |

## C. Web側の回答だけでは確定しない事項

| 項目 | 確認・調整する相手 |
| --- | --- |
| カードの規格・データ配置・認証・SDK、取得値の型や桁数 | カード／サービス仕様の管理者・端末実装担当。Web側の希望する表示形式と合わせて決める |
| 別アプリ向けのIntent・公開入口・許可する呼び出し元・結果返却方式 | Android担当と呼び出し元アプリ担当 |
| バックエンドのCORS・Cookie・認証連携 | Web担当とバックエンド担当 |

Web担当へカードの秘密情報や、Androidの外部公開設定まで回答を求めるものではありません。

## 回答の進め方

まずA1〜A6を共有し、未確定の項目は「未定・確認先・確認予定」が分かれば十分です。BはVue組み込み検証と並行して詰めます。

既存Vueを使わない、手書きHTMLによるREADY・公開テストAPI・疑似NFCイベントの単体通信検証は、これらの回答を待たずに進められます。既存Vueの組み込みや実際の認証・業務APIまで検証する前に、必要な回答をそろえる扱いです。
